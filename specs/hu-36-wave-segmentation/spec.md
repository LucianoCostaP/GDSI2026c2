## User Scenarios & Testing *(mandatory)*

### User Story 1 - Segment Socios into Waves (Priority: P1)

As a System Administrator, I want to automatically generate the segmentation of Socios into waves based on their ranking position, so that I establish the groups that will access turn reservation in a staggered way.

**Why this priority**: Waves turn the ranking into actual priority.

**Independent Test**: For a published event with capacity and a completed ranking, trigger segmentation and verify wave count, band sizes, the final wave with the remainder, and the per-wave output.

**Acceptance Scenarios**:

1. **Given** a `published` event with capacity and a `completed` ranking, **When** the Administrador triggers segmentation, **Then** the process starts for that event and records the ranking version it uses.
2. **Given** the process, **When** it computes the number of waves, **Then** it applies the rule: let M be the number of enabled Socios and K the capacity; if M ≤ K there is 1 wave, otherwise waves = min(maximum waves, ceil(M / K)). [NEEDS CLARIFICATION: confirm the rule and the maximum (default 10).]
3. **Given** N waves, **When** the ranking is divided, **Then** wave 1 holds the best positions: waves 1 to N−1 hold exactly floor(M / N) Socios each, in ranking order.
4. **Given** the bands, **When** the last wave is defined, **Then** it is the final wave and holds all remaining Socios, so it can hold up to N−1 more than the others.
5. **Given** a generated segmentation, **When** it is shown, **Then** it includes, per wave, its order, the position range, the percentile range and its Socios.
6. **Given** an event without a published state, without capacity, or with no completed ranking, **When** the Administrador triggers segmentation, **Then** it is not possible and the missing prerequisite is stated.
7. **Given** a segmentation already exists and the first wave has not opened, **When** the Administrador generates it again, **Then** after confirmation it replaces the previous one and any existing schedule (HU-37) is invalidated.
8. **Given** the first wave already opened, **When** the Administrador tries to generate again, **Then** it is blocked.
9. **Given** later ranking recalculations, **When** they complete, **Then** the generated waves do not change (the segmentation is a snapshot).

---

### Edge Cases

- **Enabled Socios**: Socios in the completed ranking (fees up to date at that ranking's calculation) at the moment of segmentation; fee status is re-checked at generation using synchronized data (HU-N2), and Socios overdue at that moment are left out.
- **Remainders**: left over by uneven division, they fall in the final wave.
- **Socios outside the snapshot** (joined or became up-to-date afterwards) are not in any wave; HU-39 explains it.
- **Capacity above Socios**: one wave, so the schedule has a single opening.
- **Not in scope**: Abonados and seat transfers (the role no longer exists).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST let the Administrador trigger segmentation for a specific published event with capacity and a completed ranking.
- **FR-002**: System MUST compute the number of waves from enabled Socios and event capacity using the rule above.
- **FR-003**: System MUST divide the ranking into contiguous bands of equal size by position.
- **FR-004**: System MUST make the last wave (lowest percentile) the final wave, grouping every Socio not covered by earlier bands.
- **FR-005**: System MUST include, per wave, the percentile range, the position range and its Socios.
- **FR-006**: System MUST store the segmentation as a snapshot tied to a ranking version.
- **FR-007**: System MUST allow regeneration only before the first wave opens, invalidating the schedule.
- **FR-008**: System MUST audit every generation.

### Key Entities

- **WaveSegmentation**: event, ranking version, enabled Socios, capacity, number of waves, generated at, generated by.
- **Wave**: order, position range, percentile range, member Socios.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of enabled Socios belong to exactly one wave.
- **SC-002**: Waves 1 to N−1 have exactly floor(M / N) Socios and the last holds the rest.
- **SC-003**: 0 waves change after a later ranking calculation.

## Assumptions

- Wave 1 is the highest-ranked group; "lowest percentile" is the last wave.
- The number-of-waves rule is a default proposal; changing it only changes a function, not the rest of the flow.
- The Abonado exclusion is out of scope, not a requirement; it can return with the Abonado stories.
