**Status**: Draft
**Backlog Reference**: HU-15 (Estimate: 3, Priority: Media, MVP: No, to be confirmed with the team)
**Shared rules**: [scoring model](../_shared/scoring-model.md), [cross-cutting](../_shared/cross-cutting.md), [data contract](../_shared/data-contract.md)
**Input**: "Como Socio del club quiero consultar el historial de eventos a los que accedí y las reglas que estaban vigentes en cada uno para entender cómo se determinó mi participación y prioridad en el pasado."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - View My Event History with the Rules Applied (Priority: P2)

As a Socio of the club, I want to see the past events I attended and the scoring rules that were in force at each one, so that I understand how my participation and priority were determined.

**Why this priority**: It completes the transparency started by HU-13 (current rules) and HU-16 (breakdown): the Socio can trace each past attendance to the rules version that counted it.

**Independent Test**: Publish rules v1 (HU-27), load attendance for a past Partido (HU-24), adjust the rules to v2 (HU-28), load attendance for a later institutional event. Log in as the Socio and verify that both events appear, most recent first, with date and type, and that the first links to rules v1 and the second to rules v2. Open each link and verify the explanation of that version. A newly activated Socio with no attendance sees the empty-history message.

**Acceptance Scenarios**:

1. **Given** a Socio with attendance registered in several past events of their club, **When** they open their event history, **Then** every one of those events is listed once, ordered chronologically from the most recent to the oldest.
2. **Given** the history, **When** it renders, **Then** each event shows its title, its date and time (Buenos Aires time) and its type (`Partido` or `Evento institucional/amateur`). The class of a Partido is not shown (as in HU-17).
3. **Given** an event of the history, **When** the rules version in force at the event's start was version N, **Then** the event shows "Reglas versión N" with a link to see those rules; the link opens the explanation of version N generated by the same function as HU-13, even if version N is now `superseded`.
4. **Given** an event that took place before the club published any rules, **When** the history renders, **Then** the event shows "No había reglas de puntaje publicadas en ese momento." and no link.
5. **Given** the history or the rules of a version, **When** the Socio interacts with them, **Then** they are read-only: there is no control to change anything and the server rejects any non-GET method.
6. **Given** a Socio with no attendance registered (for example, they just activated their account), **When** they open their history, **Then** the message "Todavía no tenés eventos en tu historial. Cuando el club registre tu asistencia a un evento, lo vas a ver acá." is shown instead of an empty list.
7. **Given** two clubs, **When** a Socio opens their history or asks for a rules version, **Then** they only get events and rules of their own club; a rules version number of another club (or that does not exist) is answered as not found.
8. **Given** a Socio with overdue fees, **When** they open their history, **Then** it is shown normally (the history is kept whatever the fee status, decision 7).
9. **Given** an Admin or a request without session, **When** they request the Socio's history or a rules version, **Then** it is rejected.
10. **Given** a logged-in Socio, **When** they look for the history, **Then** they find it from the side navigation bar ("Mi historial").

---

### Edge Cases

- **"Accessed" means attended**: in the MVP the only per-Socio record of access to an event is the attendance loaded by the club (HU-24). An event appears if there is a definitive attendance row (`asistencias`) of the Socio's document in that club. Events without attendance loaded, events in `pending importance definition` or `discarded`, and loads in `pending approval` or `rejected` do not count.
- **Published and historical events**: both a `published` event that already happened and a `historical` event with confirmed class or points appear.
- **Rules in force at an event**: the rules version of the club with the latest `published_at` that is less than or equal to the event start (`fecha_hora`). A version published exactly at the start counts as in force. Comparisons are in UTC.
- **Same moment**: two events at the same date and time are ordered by internal id so the order is stable.
- **Duplicated attendance**: a Socio listed twice in the same event appears once.
- **Socio without roster copy**: if the account has no matching Socio in the club's roster (same club and document), the history is empty (scenario 6), not an error.
- **Club of the Socio**: comes from the account (decision 34), never from a request parameter.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST list the past events of the Socio's club with a definitive attendance of the Socio, each once, from the most recent to the oldest.
- **FR-002**: System MUST show for each event its title, date and time in Buenos Aires time and its type, and MUST NOT show the class.
- **FR-003**: System MUST indicate for each event the rules version in force at its start, or that there were none, and offer a link to that version.
- **FR-004**: System MUST let the Socio read any rules version of their own club by its number, generated by the same function as HU-13 (FR-008 of HU-13).
- **FR-005**: System MUST present the history and the rules as read-only.
- **FR-006**: System MUST show the empty-history message when there are no events.
- **FR-007**: System MUST restrict both endpoints to Socios and to their own club, enforced on the server.

### Key Entities

- **EventHistoryItem**: event (internal id, title, start, type) plus a reference to the rules version in force at its start (number, publication date) or none. Derived, not stored.
- **RulesVersion** (existing, HU-27): read by number within the club; never modified.

### API

Under the Socio's session; the club comes from the account (decision 34). No aliases; `club_id` or `X-Club-ID` are ignored if they arrive. Both responses carry `Cache-Control: no-store`.

- `GET /member/events/history` → 200 `{status, message, total, events}`.
  - `status`: `ok` or `empty`. With `empty`, `message` has the text above, `total` is 0 and `events` is `[]`.
  - `events[]`: `{id_interno, titulo, fecha_hora, tipo, rules_version, rules_message}`. `fecha_hora` is ISO 8601 UTC (the front shows Buenos Aires time). `tipo` is `Partido` or `Evento institucional/amateur`. `rules_version` is `{number, published_at, url}` with `url = /member/scoring/rules/{number}`, or `null` with `rules_message` set to the text of scenario 4.
- `GET /member/scoring/rules/{number}` → 200 `{rules_version, published_at, in_force, formula: {id, version, name}, explanation}`. `explanation` is the same object as HU-13. It never includes who published the rules or the formula lock. 404 `RULES_VERSION_NOT_FOUND` otherwise.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the events with definitive attendance of the Socio appear, and 0 events without it.
- **SC-002**: For every event, the rules version shown equals the latest version published at or before its start.
- **SC-003**: The explanation of a version is identical to the one HU-13 / HU-27 produce for the same values.

## Assumptions

- Decision 50 (proposed): the Socio can read past rules versions of their club, read-only, only through this story. It narrows decision 41 (no version history screen): there is still no list of versions, only the version linked from each event.
- "Ordenados cronológicamente" is read as most recent first, like any history; to be confirmed by the Product Owner.
- The rules in force at the event are the ones that were published, not necessarily the ones of the ranking used for that event's waves (HU-36). Showing the ranking used per event is a possible extension.
